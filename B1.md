# B1 — The Glacier cost gotcha

What's the actual cost impact of an early deletion after archival? How would you redesign the
lifecycle so this stops quietly costing more than budgeted?

The lifecycle rule transitions every object in `haven-listing-media` to storage class `GLACIER`
30 days after creation. In the AWS provider that class is S3 Glacier Flexible Retrieval. The
provider region in this repo is `us-east-1`.

A photo uploaded on day 0 is archived on day 30. The seller asks for deletion on day 40, and
the object is deleted the same day. It has been in Glacier for 10 days.

## What that delete actually costs

S3 Glacier Flexible Retrieval has a minimum storage duration of 90 days. Deleting, overwriting,
or transitioning an object before those 90 days are up bills the storage already used and a
second, prorated charge for the days that were left. The second charge is `EarlyDelete-ByteHrs`,
priced at the Glacier Flexible Retrieval storage rate. `DeleteObject` does not restore the
object, so this is not a retrieval fee. DELETE requests themselves are free. The charge is for
the time the object did not stay.

For this photo, 80 days of the minimum are left (90 − 10). At the published us-east-1 rate of
$0.0036 per GB-month, each GB deleted on day 40 costs about:

- $0.0012 for the 10 days already stored (`10/30 × 0.0036`)
- $0.0096 for the 80 days remaining (`80/30 × 0.0036`), billed after the object is gone

Plus a lifecycle transition request into Glacier, and the 40 KB of metadata S3 adds for every
Flexible Retrieval object (8 KB at Standard rates, 32 KB at Glacier rates). That metadata is
under the same 90-day minimum, which is a large fraction of the bill when the photo is small.

The budget assumption behind the rule is that day 30 is when storage gets cheap. For an object
deleted on day 40 it does not. The early-delete line is the same order of cost as leaving the
object in Glacier until day 120, and the bytes are already deleted, so the savings the rule was
chosen for never occur. The charge shows up under an early-delete usage type rather than as
"listing media storage," which is why it overruns the budget without looking like the bucket
grew.

Waiting is not an escape. The application has to delete within 30 days of the seller's request.
A request on day 40 has a deadline of day 70. The Glacier minimum, counted from the transition
on day 30, runs until day 120. Using the whole legal window still leaves 50 days of
`EarlyDelete-ByteHrs`. Any listing a seller can still demand deleted cannot honestly be put in
this class.

The rule makes that worse than the story in the comment. It sets no `filter` and no `prefix`,
so the transition applies to the whole bucket, not only to sold-listing photos. The plan warns
that a future provider will reject the rule until one of those is set.

`GLACIER_IR` has the same 90-day minimum. `DEEP_ARCHIVE` has 180. Moving the transition to
either one does not fix the bill. Standard-IA is not the fix either: its minimum is 30 days, so
a transition on day 30 and a delete on day 40 still generates an early-delete charge, at a
higher per-GB rate.

## Redesign

Sold-listing photos can be deleted on a 30-day deadline at any time, so this bucket cannot
promise 90 days of Glacier residency. Stop transitioning it to `GLACIER`.

Keep the day-30 cost drop, scoped to the objects the comment actually names, and use a class
whose automatic tiers have no minimum duration:

```hcl
resource "aws_s3_bucket_lifecycle_configuration" "listing_media_archive" {
  bucket = aws_s3_bucket.listing_media.id

  rule {
    id     = "tier-sold-listing-photos"
    status = "Enabled"

    filter {
      prefix = "sold/"
    }

    transition {
      days          = 30
      storage_class = "INTELLIGENT_TIERING"
    }
  }
}
```

S3 Intelligent-Tiering's Frequent, Infrequent, and Archive Instant Access tiers have no minimum
storage duration and no retrieval fee. A day-40 delete then bills the days the object was
actually stored. The class adds a small per-object monitoring charge, and objects under 128 KB
stay in Frequent Access and are not monitored. That is the trade that removes the surprise
80-day charge.

Do not enable the optional Intelligent-Tiering Archive Access or Deep Archive Access tiers on
this bucket. Those tiers bring the 90-day and 180-day minimums back, and a delete inside the
window is `EarlyDelete-ByteHrs` again.

Glacier still fits objects that have a real retention contract. A separate rule can transition
only objects tagged with something like `retention = "glacier-90"`, and only the application
path that will not issue a delete until 90 days after that transition is allowed to set the
tag. Sold listings that accept a deletion request do not get the tag. An expiration shorter
than 90 days after a Glacier transition would manufacture the same fee on purpose, so it does
not belong on that rule.

The lifecycle change is what stops the overrun. A budget or anomaly alarm on
`EarlyDelete-ByteHrs` for this bucket is the backstop, so a later rule cannot recreate the
charge quietly. This redesign is the written answer; `terraform/lifecycle.tf` is left as the
rule the plan reproduces.
