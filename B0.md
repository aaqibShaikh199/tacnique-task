# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

Removing `la-002` from the middle of `var.landlord_accounts` does not plan "destroy the la-002
bucket." `count` addresses each bucket by position, and the seeded state is:

| Address | Bucket | Tag |
|---|---|---|
| `aws_s3_bucket.landlord_media[0]` | `haven-media-la-001` | `la-001` |
| `aws_s3_bucket.landlord_media[1]` | `haven-media-la-002` | `la-002` |
| `aws_s3_bucket.landlord_media[2]` | `haven-media-la-003` | `la-003` |
| `aws_s3_bucket.landlord_media[3]` | `haven-media-la-004` | `la-004` |

The list becomes `["la-001", "la-003", "la-004"]`. Index 0 is still `la-001`. Every index after
the removal now names a different account, and index 3 no longer exists.

## What `terraform plan` shows

Reproduced with Terraform 1.7.5 and `hashicorp/aws` 5.100.0, against the seeded state, without
writing that state back:

```bash
# variables.tf default temporarily set to ["la-001", "la-003", "la-004"]
terraform plan -refresh=false -input=false
```

`-refresh=false` is required. A refresh against the dummy credentials returns 403, Terraform
drops the "missing" buckets out of state, and the plan becomes a set of fresh creates. That
hides the shift.

`landlord_media[0]` is absent from the plan. The other three are not:

```text
# aws_s3_bucket.landlord_media[1] must be replaced
-/+ resource "aws_s3_bucket" "landlord_media" {
      ~ bucket = "haven-media-la-002" -> "haven-media-la-003" # forces replacement
      ~ tags   = { "landlord_account_id" = "la-002" -> "la-003" }
    }

# aws_s3_bucket.landlord_media[2] must be replaced
-/+ resource "aws_s3_bucket" "landlord_media" {
      ~ bucket = "haven-media-la-003" -> "haven-media-la-004" # forces replacement
      ~ tags   = { "landlord_account_id" = "la-003" -> "la-004" }
    }

# aws_s3_bucket.landlord_media[3] will be destroyed
# (because index [3] is out of range for count)
- resource "aws_s3_bucket" "landlord_media" {
      - bucket = "haven-media-la-004" -> null
      - tags   = { "landlord_account_id" = "la-004" } -> null
    }
```

Terraform prints `destroy and then create replacement` for `[1]` and `[2]`. The same plan also
creates `aws_s3_bucket.listing_media` and its lifecycle configuration, because those resources
are in config and were never in the seeded state. They are not part of the index shift. The
landlord-media actions are 2 replacements and 1 destroy. `variables.tf` was restored after this
plan; the seeded state checksum did not change.

## Why that is dangerous here

Each of these buckets is a landlord's media, and `bucket` on `aws_s3_bucket` forces a new
resource. S3 cannot rename a bucket in place, and Terraform does not copy the objects into the
replacement.

The account that was removed is `la-002`. The plan also destroys the buckets that still belong
to `la-003` and `la-004`:

- `[1]` destroys `haven-media-la-002`, then creates a new empty bucket named `haven-media-la-003`.
- `[2]` destroys the real `haven-media-la-003` (that is `la-003`'s media), then creates a new
  empty `haven-media-la-004`.
- `[3]` destroys the real `haven-media-la-004`.

`la-001` survives only because it stayed at index 0. Two landlords who were not offboarded lose
their objects. The tag moves with the index, so the new empty bucket at `[1]` is billed as
`la-003`.

The two replacements also want the same name at different moments. `[1]` creates
`haven-media-la-003` and `[2]` destroys that same name. Nothing in the graph orders `[2]`'s
destroy before `[1]`'s create. If the create runs first, apply fails with `BucketAlreadyExists`
after some destroys may already have happened. If the destroy runs first, the apply succeeds
and the media is gone. Either result is an outage caused by deleting one string from a list.

## The fix

Address the bucket by the account id, not by its position. `for_each` gives every account a
stable address, so removing `la-002` destroys only `aws_s3_bucket.landlord_media["la-002"]`.

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)

  bucket = "haven-media-${each.value}"

  tags = {
    landlord_account_id = each.value
  }
}
```

Switching this seeded state straight to `for_each` is a second destroy. Terraform would see
`[0]`–`[3]` as removed and `"la-001"`–`"la-004"` as new, and would recreate `la-001` along with
everyone else. The addresses have to move before that plan is applied. `la-002` is the index
that should not move; it is the one that gets destroyed.

```hcl
moved {
  from = aws_s3_bucket.landlord_media[0]
  to   = aws_s3_bucket.landlord_media["la-001"]
}

moved {
  from = aws_s3_bucket.landlord_media[2]
  to   = aws_s3_bucket.landlord_media["la-003"]
}

moved {
  from = aws_s3_bucket.landlord_media[3]
  to   = aws_s3_bucket.landlord_media["la-004"]
}
```

The equivalent one-off commands are `terraform state mv` for those three addresses. After the
move, later additions and removals only touch the key that changed. Order in the list stops
being identity.

This fix is written here and is not applied in `terraform/main.tf`. That file, plus the seeded
state, is what makes the plan above reproducible. Applying `for_each` without the `moved`
blocks would destroy the reproduction and the buckets.
